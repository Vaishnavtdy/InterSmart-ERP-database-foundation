# Step 20 — Audit Logs / Activity History / System Administration Controls

You are continuing development of the existing **InterSmart Internal ERP**.

This is **Step 20 only**.

## Objective

Implement the database layer for:

1. System-wide audit logs
2. User activity history
3. Authentication/security events
4. Data change tracking
5. Login/session history
6. Security event tracking
7. Administrative activity tracking
8. Entity activity timeline
9. API/request activity metadata where appropriate

Do NOT implement frontend pages, APIs, controllers, services, middleware, authentication logic, or audit interceptors in this step.

---

# 1. IMPORTANT ARCHITECTURE RULE

Before making changes:

- Inspect the complete Prisma schema.
- Reuse the existing `users`, `roles`, `permissions`, `projects`, `tasks`, `customers`, `payments`, `bugs`, HR models, etc.
- Do not create separate audit tables for every module.
- Do not duplicate existing status-history tables.
- Do not replace existing business history tables.
- Do not store sensitive credentials.
- Do not store passwords.
- Do not store access tokens.
- Do not store refresh tokens.
- Do not store API keys.
- Do not store private keys.
- Do not store complete request/response bodies blindly.

The audit system is an **additional cross-module audit layer**, not a replacement for domain-specific history tables.

# 2. AUDIT LOG

- `id` UUID PK
- `user_id` nullable FK → users

- `entity_type`
- `entity_id` nullable
- `description` nullable
- `ip_address` nullable
- `user_agent` nullable
- `request_id` nullable

```text id="h7x3q4"
PERMISSION_CHANGED
ROLE_CHANGED

APPROVAL

DOWNLOAD
UPLOAD
OTHER
```

Do not create a separate table for each action.

# 3. ENTITY REFERENCE

Use:

```text id="1m8j6n"
entity_type
entity_id
```

to identify the affected business record.

Examples:

```text id="3r9p5v"
entity_type = PROJECT
entity_id = project UUID
```

or:

```text id="8q2x6k"
entity_type = PAYMENT
entity_id = payment UUID
```

This allows a common audit system to support:

- Projects
- Customers
- Leads
- Proposals
- Payments
- Tasks
- Bugs
- HR records
- Meetings
- Infrastructure
- Reports

Do not create dozens of nullable foreign keys.

# 4. AUDIT METADATA

`metadata` may contain safe contextual information such as:

```text id="0y3s6m"
changed_fields
old_status
new_status
source
module
reason
browser
request context
```

However:

## NEVER store:

```text id="v8g2s1"
password
password_hash
access_token
refresh_token
JWT
API key
AWS secret
SSH private key
database password
SMTP password
MinIO secret
TLS private key
Git credentials
```

If sensitive data appears in a request, the future audit middleware must sanitize it before writing metadata.

---

# 5. DATA CHANGE DETAILS

For important updates, metadata may contain:

```json
{
  "changedFields": [
    "status",
    "priority"
  ]
}
```

Do not automatically store an entire before/after object for every database update.

This can create:

- huge audit records
- privacy risks
- sensitive data leakage
- poor database performance

The application layer should selectively record meaningful changes.

# 8. LOGIN/SESSION HISTORY

Create:

## `user_sessions`

Fields:

- `id` UUID PK
- `user_id` FK → users
- `session_identifier` UNIQUE
- `ip_address` nullable
- `user_agent` nullable
- `created_at`
- `last_activity_at`
- `expires_at`
- `revoked_at` nullable
- `revoked_by_id` nullable FK → users
- `revoke_reason` nullable

Important:

`session_identifier` must NOT contain the actual authentication token.

Store only a safe identifier/reference.

If the future authentication implementation uses refresh tokens, do not store raw tokens here.

# 12. DOMAIN HISTORY VS AUDIT

Follow this rule:

### Domain history

Stores business lifecycle information.

Example:

```text id="4v7n2p"
Task moved from IN_PROGRESS → COMPLETED
```

### Audit log

Stores who performed the operation and relevant security/context information.

Example:

```text id="6k3w9s"
User 123 changed task status
IP: ...
Request ID: ...
```

Do not remove existing history tables.

Do not duplicate every history record unnecessarily.

---

# 13. REQUEST ID

`audit_logs.request_id` should allow multiple actions from one HTTP/API request to be correlated later.

Example:

```text id="s6n8p2"
request_id = 7d1c...
```

The actual request ID generation will be implemented later in the backend.

Do not implement request middleware now.

---

# 14. IP ADDRESS

Use a database type compatible with PostgreSQL IP address storage if practical.

Prefer PostgreSQL `inet` if the project's Prisma version supports the required mapping cleanly.

Otherwise use a sufficiently sized string field.

Do not store geolocation coordinates.

Do not attempt to infer the employee's physical location.

---

# 15. USER AGENT

`user_agent` may contain the browser/client user-agent string.

Do not parse and permanently store unnecessary browser metadata such as:

- exact device fingerprint
- hardware identifiers
- tracking IDs

unless a future security requirement explicitly requires it.

# 16. RETENTION SUPPORT

Audit data can grow significantly.

The schema should support future retention policies.

Use:

```text id="h9w3s2"
created_at
```

on all audit/security/history tables.

Do not implement automatic deletion in this step.

Do not create cron jobs.

Future retention policies can archive/delete old audit records according to company policy.

# 18. SECURITY / PRIVACY

Audit logs themselves may contain sensitive business information.

Therefore:

- Access should be restricted.
- Normal employees should not automatically see all audit logs.
- HR records require special access.
- Financial audit records require appropriate permissions.
- Security events should be restricted to authorized administrators.
- User activity history should be limited according to role.

Do not implement the authorization layer in this migration.

Prepare the schema for it.
