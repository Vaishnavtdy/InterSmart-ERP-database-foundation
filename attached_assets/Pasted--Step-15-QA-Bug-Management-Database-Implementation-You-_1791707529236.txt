# Step 15 — QA & Bug Management Database Implementation

You are continuing the incremental database implementation for the InterSmart internal ERP.

## Current architecture

The application is for **one organization: InterSmart**.

Important architecture rules:

- Do NOT create an `organizations` table.
- Do NOT add `organization_id` or `tenant_id`.
- `users` are internal InterSmart employees.
- `customers` are external clients and do not authenticate.
- PostgreSQL + Prisma.
- UUID primary keys.
- PostgreSQL `timestamptz` through Prisma `DateTime`.
- `Decimal` for monetary values.
- Existing Project, Task, Team, File, UI, UX, Development, Budget, and Payment models must be reused.
- No AWS services.
- Do NOT reset the database.
- Do NOT delete or rewrite old migrations.
- Create a new migration only for this step.

# 28. Bug verification workflow

The expected application workflow is:

```text
QA creates Bug
        ↓
TRIAGED
        ↓
Developer assigned
        ↓
IN_PROGRESS
        ↓
FIXED
        ↓
READY_FOR_RETEST
        ↓
QA verifies
        ↓
VERIFIED
        ↓
CLOSED
```

If verification fails:

```text
VERIFIED
   ↓
REOPENED
   ↓
IN_PROGRESS
```

The database should support this lifecycle but should not hard-code every transition.
