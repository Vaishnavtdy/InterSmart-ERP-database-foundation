==================================================
1. PROPOSAL
==================================================

A Proposal represents a commercial proposal prepared by the Sales team for a lead/customer.

Fields:

- id UUID primary key
- proposalCode unique
- leadId nullable
- customerId
- createdById
- title
- status
- currentVersionId nullable
- validUntil nullable
- createdAt
- updatedAt
- deletedAt nullable

RELATIONSHIPS:

Proposal
 ├── Lead nullable
 ├── Customer
 ├── Created By User
 ├── Proposal Versions[]
 └── Current Version

IMPORTANT:

leadId MUST be nullable.

A proposal may be created from an existing lead, but the database should not force every proposal to have a lead.

customerId is required because a proposal must belong to a customer.

==================================================
2. PROPOSAL VERSION
==================================================

Proposal pricing and commercial details must be versioned.

Do NOT overwrite an old proposal version.

Fields:

- id UUID primary key
- proposalId
- versionNumber
- status
- subtotal
- discountAmount
- taxAmount
- totalAmount
- notes nullable
- validUntil nullable
- createdById
- createdAt
- sentAt nullable
- acceptedAt nullable
- rejectedAt nullable
- rejectionReason nullable

Use Decimal for:

- subtotal
- discountAmount
- taxAmount
- totalAmount

Every proposal should be able to have multiple versions:

Version 1
Version 2
Version 3
...

A proposal should have only one current version.

Use an appropriate unique constraint such as:

proposalId + versionNumber

==================================================
3. PROPOSAL ITEM
==================================================

Proposal items belong to a specific proposal version.

Fields:

- id UUID primary key
- proposalVersionId
- description
- quantity
- unitPrice
- discountType nullable
- discountValue nullable
- amount
- sortOrder
- createdAt
- updatedAt

Use Decimal for:

- quantity where appropriate
- unitPrice
- discountValue
- amount

Do NOT use floating-point types for monetary values.

==================================================
DISCOUNT TYPE
==================================================

Support:

PERCENTAGE
FIXED

Example:

Item price = ₹100,000

PERCENTAGE:
discountValue = 10

FIXED:
discountValue = 10,000

The actual calculated amount should be stored as Decimal if it represents a finalized commercial snapshot.

==================================================
VERSION STATUS
==================================================

Use an appropriate status for versions.

Recommended:

DRAFT
ACTIVE
SUPERSEDED
ACCEPTED
REJECTED
CANCELLED

A proposal version should become SUPERSEDED when a newer version replaces it.

Do not physically delete old versions simply because a new version is created.

==================================================
MONEY / CALCULATION RULES
==================================================

Use PostgreSQL NUMERIC / Prisma Decimal.

Never use:

Float
Double
JavaScript floating-point arithmetic as the database source of truth.

The backend will later calculate:

subtotal
discount
tax
total

and save the finalized commercial values.

Do not store unnecessary derived totals at multiple levels.

For example:

Proposal does NOT need its own totalAmount if ProposalVersion already represents the commercial amount.
