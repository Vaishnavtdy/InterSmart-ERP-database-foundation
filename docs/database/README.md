# Database

InterSmart ERP uses PostgreSQL with Prisma. The Prisma package and schema are
located in `packages/database/`.

## Requirements

- Set `DATABASE_URL` to the PostgreSQL connection string through the workspace
  secrets/environment settings. Do not commit connection strings.
- Use Prisma Migrate for schema changes; do not use schema push or reset
  commands against an existing database.

## Commands

Run from the repository root:

```sh
pnpm --filter @workspace/database run db:format
pnpm --filter @workspace/database run db:validate
pnpm --filter @workspace/database run db:generate
pnpm --filter @workspace/database run db:migrate:dev --name <change-name>
pnpm --filter @workspace/database run db:migrate:deploy
pnpm --filter @workspace/database run db:migrate:status
pnpm --filter @workspace/database run db:seed
```

`db:migrate:dev` is for local development and creates a migration from a
reviewed schema change. `db:migrate:deploy` applies committed migrations and is
intended for controlled deployment workflows.

## Employee foundation

The approved employee foundation contains `users`, `departments`, and
`employee_profiles`. The nine department codes are seeded by the idempotent
`db:seed` command. No roles or other ERP modules are included.

For a new database, create and apply a development migration with:

```sh
pnpm --filter @workspace/database run db:migrate:dev --name employee_foundation --create-only
pnpm --filter @workspace/database run db:migrate:deploy
pnpm --filter @workspace/database run db:seed
```

Review migration SQL before applying it. The first migration is
`20261010095510_employee_foundation`.

The seed inserts missing department codes in a transaction and does not create
user accounts. It can be rerun without adding duplicate department records.

## Tables and constraints

| Table | Purpose |
| --- | --- |
| `departments` | Nine controlled department codes, UUID IDs, and timestamps |
| `users` | Employee identity, password hash, department, manager, and account state |
| `employee_profiles` | Optional job title, work location, and biography for one user |

- All three primary keys use native PostgreSQL UUID columns, with UUID values
  generated by Prisma.
- All timestamps, including `joining_date`, use `TIMESTAMPTZ(6)`. `updated_at` is
  maintained by Prisma on updates.
- User status is `ACTIVE`, `INACTIVE`, or `SUSPENDED` (default `ACTIVE`).
- `phone`, `manager_id`, `last_login_at`, and `deleted_at` are nullable.
  Department assignment and joining date are required.
- A profile is optional; when present, its `user_id` is required and unique.
  Its job title, work location, and biography are nullable.
- Employee code and email are unique. Email uniqueness is PostgreSQL's
  case-sensitive string uniqueness; the eventual account-writing API must
  normalize and validate email before storing it.
- Unique constraints provide indexes for email, employee code, department
  code, and profile-to-user lookup. Additional user indexes cover
  `(department_id, status)`, `manager_id`, `joining_date`, and
  `(status, deleted_at)`.
- Department deletion is restricted while it has users. Hard-deleting a
  manager clears reporting users' `manager_id`; hard-deleting a user cascades
  to its profile. Normal employee removal should use soft deletion instead.
- A migration-level check rejects `manager_id = id`. Reporting-cycle checks
  across several employees are not implemented in this database-only step.

`users.deleted_at` is a nullable soft-delete marker. Employee codes and email
addresses remain unique even after soft deletion so historical identifiers are
not reused.

The existing Drizzle scaffold under `lib/db/` is preserved and has not been
converted or deleted in this step. New ERP schema work belongs in
`packages/database/prisma/schema.prisma`. Do not run the legacy Drizzle
schema-push commands against the ERP database.

## Customers (Database Step 3)

Migration: `20261010100740_customers`.

External customers do not authenticate. Their contacts are not employee users
and have no role or permission links. No APIs or frontend screens are included.

| Table | Fields |
| --- | --- |
| `customers` | UUID `id`; unique `customer_code`; required `company_name`; nullable `website`, `industry`, `country`, `state`, `city`, `address`, `source`; `status`; nullable `assigned_salesperson_id`; `created_at`, `updated_at`; nullable `deleted_at` |
| `customer_contacts` | UUID `id`; required `customer_id`, `first_name`; nullable `last_name`, `email`, `phone`, `designation`; `is_primary`, `status`; `created_at`, `updated_at` |

- Customer status: `ACTIVE`, `INACTIVE`, `PROSPECT` (default), `BLOCKED`.
- Contact status: `ACTIVE` (default), `INACTIVE`; `is_primary` defaults to false.
- Native UUID IDs and `TIMESTAMPTZ(6)` timestamps follow the employee foundation.
- A nullable salesperson references an existing user. Hard-deleting that user
  clears assignment without deleting customers.
- A customer can have many contacts and zero or one primary contact. A
  PostgreSQL partial unique index on `customer_id WHERE is_primary = true`
  enforces this even for concurrent writes. This SQL-only index must be retained
  when reviewing future migrations; do not replace it with an unconditional
  unique constraint on `customer_id`, which would allow only one contact total.
- Hard-deleting a customer cascades to its contacts; normal customer removal
  uses `deleted_at` and retains contacts. Inactive contacts marked primary still
  occupy the primary slot until explicitly demoted.
- Indexes cover unique customer code, company name, `(status, deleted_at)`,
  salesperson assignment, contact customer lookup, contact email, and phone.
  Contact email and phone are deliberately not unique.
- The existing seed remains department-only; this module requires no seed data.

**Repository observation:** Step 2 roles/permissions models and migration were
not present when Step 3 was implemented. They have not been recreated or added.

## Leads (Database Step 4)

Migration: `20261010101229_leads`, containing only additive lead-module changes.

This database-only module adds `leads` and `lead_activities`. A lead can be
captured before a customer exists. Customers remain external business entities,
not authenticating ERP users. No controllers, services, DTOs, screens,
notifications, proposals, or projects are added.

| Table | Fields |
| --- | --- |
| `leads` | UUID `id`; unique `lead_code`; nullable `customer_id`; required `assigned_to_id`, `source`, `contact_name`; nullable `email`, `phone`, `company_name`, `requirement`, `estimated_value`, `expected_close_date`; `status`, `temperature`; nullable `notes`; `created_at`, `updated_at`; nullable `deleted_at` |
| `lead_activities` | UUID `id`; required `lead_id`, `user_id`, `activity_type`, `subject`; nullable `description`, `scheduled_at`, `completed_at`, `next_follow_up_at`; `created_at` |

- Lead status: `NEW` (default), `FOLLOW_UP`, `MEETING`, `PROPOSAL`,
  `READY_TO_CLOSE`, `WON`, `LOST`.
- Temperature: `COLD` (default), `WARM`, `HOT`.
- Required source: `WEBSITE`, `REFERRAL`, `SOCIAL_MEDIA`, `ADVERTISEMENT`,
  `COLD_CALL`, `EMAIL`, `DIRECT`, `EXISTING_CUSTOMER`, `OTHER`.
- Activity type: `CALL`, `EMAIL`, `MEETING`, `FOLLOW_UP`, `PROPOSAL`, `NOTE`,
  `WHATSAPP`, `OTHER`.
- Estimated value is nullable `NUMERIC(18,2)` and must not be negative. Currency
  was not specified; no currency column or exchange-rate assumption is added.
  Choose a common reporting currency before aggregating these values.
- IDs/FKs are native UUIDs; timestamps are `TIMESTAMPTZ(6)`. Prisma maintains
  the lead's `updated_at`. Activities have the requested `created_at` only.
- Assigned employee and activity author FKs restrict hard deletion of users.
  Deleting a customer clears nullable lead linkage rather than deleting leads.
- Lead soft deletion retains activities. Hard deletion of a lead with
  activities is restricted, preventing accidental destruction of sales history.
- Indexes cover unique lead code, customer lookup, assigned employee/status/
  deletion state, status/deletion state, temperature/deletion state, expected
  close date, and creation date. Activity indexes cover lead/history timestamp,
  author/next follow-up time, type, scheduled time, and next follow-up time.
- No dashboard totals or conversion percentages are stored. This step adds
  no sample lead or activity seed data.
- Statuses represent the requested workflow but do not enforce transition
  order or automatically create customers/projects. Those business operations
  and their audited status changes require a separately approved implementation.

## Proposals (Database Step 5)

Migration: `20261010103125_proposals`, applied atomically with additive changes.

Only the database layer is implemented: `proposals`, `proposal_versions`, and
`proposal_items`. No project, payment, audit, notification, or approval-engine
models, application endpoints, or screens are introduced.

| Table | Fields |
| --- | --- |
| `proposals` | UUID `id`; unique `proposal_code`; nullable `lead_id`; required `customer_id`, `created_by_id`, `title`; `status`; nullable `current_version_id`, `valid_until`; `created_at`, `updated_at`; nullable `deleted_at` |
| `proposal_versions` | UUID `id`; required `proposal_id`, `version_number`, `status`, `subtotal`, `discount_amount`, `tax_amount`, `total_amount`, `created_by_id`; nullable `notes`, `valid_until`, `sent_at`, `accepted_at`, `rejected_at`, `rejection_reason`; `created_at` |
| `proposal_items` | UUID `id`; required `proposal_version_id`, `description`, `quantity`, `unit_price`, `amount`, `sort_order`; nullable `discount_type`, `discount_value`; `created_at`, `updated_at` |

- Proposal status: `DRAFT` (default), `SENT`, `UNDER_NEGOTIATION`, `ACCEPTED`,
  `REJECTED`, `EXPIRED`, `CANCELLED`.
- Version status: `DRAFT` (default), `ACTIVE`, `SUPERSEDED`, `ACCEPTED`,
  `REJECTED`, `CANCELLED`. Discount type is `PERCENTAGE` or `FIXED`.
- A proposal requires an existing customer and employee creator; its lead is
  optional. A lead can have multiple proposals.
- Each version has its own items and commercial values. `(proposal_id,
  version_number)` is unique, and version numbers must be positive.
- The optional current-version pointer is a composite FK `(id,
  current_version_id)` to version `(proposal_id, id)`, preventing references to
  another proposal's version. Create the header with a null current version,
  insert its version/items, then set the pointer in a transaction.
- Monetary fields are `NUMERIC(18,2)`; quantity is `NUMERIC(18,4)` and defaults
  to one. All money must be finite and nonnegative; quantity must be finite
  and positive. Version
  totals are required explicit values, not database-calculated defaults.
- Discount type/value must be supplied together or both omitted. Percentage
  discounts are limited to 0–100; fixed discounts use a nonnegative amount.
  Sort order defaults to zero and must be nonnegative; ties are permitted.
- Pricing lives on versions/items only. The future backend must calculate and
  validate totals using decimal arithmetic, save finalized snapshots, and
  create a new version instead of overwriting historical pricing. The schema
  does not itself make commercial columns immutable.
- Soft deletion of a proposal retains versions/items. Restrictive FKs prevent
  cascading removal of customers, creators, versions, and items. Deleting a
  linked lead clears the optional lead link, preserving the proposal.
- Indexes cover unique code, lead, customer, creator, status/deletion state,
  header validity; version owner/number and owner/ID unique keys, creator,
  status, creation time; and item version/sort order.
- No seed records are needed: enums provide the controlled status/reference
  values, and no fake commercial transactions are inserted.

Budget, payments, invoices, general tasks, department deliverables, bugs,

| `project_categories` | UUID `id`; nullable `parent_id`, `description`; `name`; unique `code`; `is_active`; `created_at`, `updated_at` |
| `project_teams` | UUID `id`; required `project_id`, `user_id`, `department_id`, `project_role`; nullable `allocation_percentage`; `assigned_at`; nullable `released_at` |
| `project_status_histories` | UUID `id`; `project_id`; nullable `from_status`; required `to_status`, `changed_by_id`; nullable `reason`; `created_at` |
| `project_comments` | UUID `id`; required `project_id`, `user_id`, internal `comment`; `created_at`, `updated_at` |
| `project_actions` | UUID `id`; required `project_id`, `assigned_to_id`, `created_by_id`, `action_type`, `title`; nullable `description`, `due_date`; `status`; nullable `completed_at`; `created_at`, `updated_at` |

- Lifecycle: `PLANNED` (default), `ONGOING`, `ON_HOLD`, `COMPLETED`, `TERMINATED`.
  Reasons are separate `ProjectStatusReason` values on history rows, not extra
  lifecycle statuses or repeated reason columns on Project.
- Priority: `LOW`, `MEDIUM` (default), `HIGH`, `URGENT`. Optional quality:
  `STANDARD`, `PREMIUM`, `HIGH`. Optional coarse platform: `WEB`, `MOBILE`,
  `CMS`, `ECOMMERCE`, `CUSTOM_WEB`; technology choices remain category records.
- Team roles: `PROJECT_MANAGER`, `PROJECT_COORDINATOR`, `UI_TL`, `UI_RESOURCE`,
  `UX_TL`, `UX_RESOURCE`, `DEV_TL`, `DEV_RESOURCE`, `QA`, `SALES`, `ACCOUNTS`.
  These are operational project roles, not authentication/access-control roles.
- Action types: `CLIENT_RESPONSE_REQUIRED`, `PAYMENT_FOLLOW_UP`,
  `CONTENT_REQUIRED`, `APPROVAL_REQUIRED`, `MEETING_REQUIRED`,
  `INTERNAL_ACTION`, `OTHER`. Action status: `PENDING` (default),
  `IN_PROGRESS`, `COMPLETED`, `CANCELLED`.
- Allocation is nullable `NUMERIC(5,2)`, bounded to 0–100; it does not enforce
  employee-wide allocation totals. Release must not precede assignment.
- A SQL partial unique index permits only one active assignment per
  `(project_id, user_id)` while retaining released assignments and allowing
  later reassignment. Release the old row before inserting its replacement.
- Status history is append-only: SQL triggers reject updates, deletes, and

  future services must update Project and insert the attributed history row
  atomically. Correct history with a new event rather than editing an old one.
- Page count is nonnegative. Known planned/actual end dates cannot precede
  a known start date. All date/time fields use `TIMESTAMPTZ(6)`.
- Hard deletion of customers, linked proposals, categories, salespeople, and
  referenced team/history/comment/action records is restricted. Optional
  manager/coordinator links use `SET NULL` if those employees can be deleted.

- Project code is explicitly supplied, independent of UUID. No code-generation,
  proposal acceptance/conversion, status-transition, or team-sync service is
  implemented. Proposal linkage is optional and deliberately not unique.

This step adds only four database models. Scope defines **what** is included or
excluded; Business Analysis defines **why** and **for whom** the project exists.
Neither is stored on Project or mixed with budgets, tasks, or execution modules.

| Table | Fields |

| `project_scope_items` | UUID `id`; `project_scope_id`, `name`; nullable `description`; `item_type`, `is_included`; nullable `estimated_hours`; `sort_order`; `created_at`, `updated_at` |
| `business_analyses` | UUID `id`; unique `project_id`; nullable `purpose`, `about_company`, `target_audience`, `usp`, `conclusion`; required `created_by_id`; nullable `updated_by_id`; `created_at`, `updated_at` |
| `competitors` | UUID `id`; `business_analysis_id`, `name`; nullable `website`, `description`, `strengths`, `weaknesses`; `created_at`, `updated_at` |

- Scope status: `DRAFT` (default), `SUBMITTED`, `APPROVED`, `REJECTED`,
  `SUPERSEDED`.
- Scope item type: `PAGE`, `FEATURE`, `FUNCTIONALITY`, `INTEGRATION`, `CONTENT`,
  `DESIGN`, `DEVELOPMENT`, `MOBILE`, `OTHER`.
- `(project_id, version_number)` is unique. A partial unique index permits
  zero or one `APPROVED` scope per project; query that record for current
  approved scope, with no duplicated pointer on Project.
- Approval actor/time must both be absent or both present. `APPROVED` status
  requires both. Populate draft items before recording approval.
- Once approval is recorded, SQL guards preserve scope identity, content,
  creator, approval attribution/time, and creation time, reject deleting the
  version, and block insertion/update/deletion/reparenting of its items.
  Status and update timestamp may still change, allowing supersession.
- To replace approved scope, future services must insert/populate a new draft,
  supersede the old approved version, and approve the new one atomically.
  No automatic supersession, workflow service, or generic approval engine is
  implemented.
- Included items default to true; explicitly set false for exclusions.
  Estimated hours use nullable `NUMERIC(10,2)` and must be finite/nonnegative;
  unknown hours remain null. Sort order defaults to zero and is nonnegative.
- Business Analysis is one optional current document per project, not a
  versioned scope record. It can contain multiple competitors and remains
  editable with last-updater attribution.
- Restrictive foreign keys prevent orphaning and cascading loss of project
  scope, items, analysis, competitors, and employee attribution. Project soft
  deletion preserves them. No new soft-delete fields or aggregate totals are
  added to these models.
- Scope indexes cover project/version number, status/creation time, creation
  time, creator, and approver. Item indexes cover scope/sort order and item
  type. Analysis indexes cover unique project, creator/updater; competitor
  lookup is indexed by analysis ID.
- No seed changes or fake project/business-analysis records are needed.
  Preserve the partial index, checks, and snapshot-protection functions/triggers
  when reviewing future migrations.

## Project Files & Resources (Database Step 8)

Migration: `20261010112103_project_files_resources`, applied transactionally.

This is a single-company InterSmart ERP. This step adds `File` (`files`) and
`ProjectResource` (`project_resources`) only. Existing modules remain intact.

**Future storage is self-hosted MinIO. PostgreSQL stores metadata and business
relationships only, not binaries, base64, blobs, file bodies, or public URLs.**
There is no MinIO client, AWS dependency, upload/download API, UI, or new
permission/approval workflow in this step.

| Table | Fields |
| --- | --- |
| `files` | UUID `id`, required `project_id`, stable UUID `file_series_id`, required `uploaded_by_id`; `file_name`, `original_name`, globally unique `storage_key`, configurable string `bucket`, `mime_type`; BIGINT `size_bytes`; nullable string `checksum`; `version`, `is_current`; `created_at`, `updated_at`; nullable `deleted_at` |
| `project_resources` | UUID `id`, required `project_id`, `file_id`, stable UUID `resource_series_id`; `resource_type`, `title`; nullable `description`; `version`, `is_current`; required `uploaded_by_id`; `created_at`, `updated_at` |

Files describe **where/how** physical objects are stored; resources describe
**what** those objects mean in a project. Resources do not duplicate storage
keys, buckets, MIME types, sizes, or checksums. Multiple business references
may point to one file within its owning project. A composite FK
`(project_id, file_id)` → `files(project_id, id)` rejects cross-project references.
Project and uploader links are required. All deletion FKs are Restrict, retaining
employee attribution and preventing cascading loss of file/resource history.

Resource types: `BRAND_BOOK`, `LOGO`, `DOMAIN`, `BROCHURE`, `PROPOSAL`,
`BUSINESS_ANALYSIS`, `UI`, `UX`, `DEVELOPMENT`, `QA`, `OTHER`.
DOMAIN classifies an uploaded domain-information document; it does not add a
domain-management or credentials module.

### Object keys and controlled access

Store the complete key using:

`projects/{project-id}/{resource-type}/{uuid}-{safe-filename}`

Example: `projects/8f1.../BRAND_BOOK/4a2...-brand-guidelines.pdf`.
The future upload service must generate the UUID, sanitize names, prohibit path
traversal/unrestricted user paths, validate object-key byte limits, and validate
the project prefix. `original_name` is display metadata, never an object path.
Bucket names are configuration, not an enum or a hard-coded default.
Optional checksums support integrity and duplicate detection; checksums are
indexed but deliberately not unique. Prefer an algorithm-tagged digest such
as `sha256:<hex>`; algorithm validation belongs to the future service.

Future access is Employee → Next.js → NestJS authorization →
project/resource permission check → controlled MinIO access. Authorization must
also check project/file deletion state. Persist bucket/key, not permanent public
URLs, signed URLs, credentials, or file content.

### Versions and historical retention

- A new file version inserts a new row with a new object key. Reuse the stable
  file series ID; never overwrite the old MinIO object or repoint its metadata
  as a revision operation.
- File revision uniqueness is `(project_id, file_series_id, version)`.
  Resource revision uniqueness is
  `(project_id, resource_type, resource_series_id, version)`.
  Both series IDs default to fresh UUIDs for new assets; explicitly reuse the
  appropriate ID for the next revision. They are grouping identifiers, not FKs
  to another entity or an extra module.
- Stable series IDs allow several logos/UI assets of the same type, each with
  version 1. Names/titles are not identity keys. Version numbers are positive,
  defaulting to 1, and `is_current` defaults to true.
- File and resource revisions are independent: a business reference revision
  may reuse a physical file. There is no artificial equality constraint on
  their version numbers or current flags.
- **One current revision per series is a future application-level rule, not
  enforced by these tables.** The existing generator does not enable native
  partial-index representation; this step follows the requested fallback
  rather than introducing a migration-only current-version index. No partial
  indexes are added for files/resources. Earlier modules' partial indexes
  remain unchanged.
- Future writers must serialize revisions per project/series, allocate unique
  version numbers, insert the new object metadata/reference, and mark replaced
  revisions non-current atomically. No such service is implemented here.
- Soft-deleting a file must also set its own `is_current=false` (SQL check).
  Future services must mark affected current resource references non-current
  in the same transaction, retain historical references, and exclude
  soft-deleted files from access/listing. This cross-table coordination is
  not automated by the database.
- Project soft deletion retains files and resources. No physical object
  deletion, history cleanup, or fake seed records are introduced.

### Indexes, sizes, and constraints

Storage-key uniqueness also indexes object-key lookup. Files have indexes on
project/current/deleted state, uploader, checksum, and creation time, plus
series/version uniqueness and the owner/ID composite FK target key.
Resources have indexes on project/type/current state, file, type, uploader,
and creation time, plus series/type/version uniqueness. Leading composite
columns cover project-only queries without redundant single-column indexes.

`size_bytes` uses nonnegative signed BIGINT, not floating point.
Prisma returns JavaScript bigint; future JSON APIs must serialize it explicitly
(for example as a decimal string) rather than lose precision. Timestamps use
TIMESTAMPTZ(6) and Prisma-maintained updatedAt. This step adds SQL checks for
nonnegative file size, positive version numbers, and non-current soft-deleted
files. No seed changes are required.

  Adjustments/history are transaction records, not duplicate active headers.
- Status: `DRAFT` (default), `ACTIVE`, `ON_HOLD`, `CLOSED`, `CANCELLED`.
- Allocation type: `PROJECT_MANAGEMENT`, `BUSINESS_ANALYSIS`, `UI`, `UX`,
  `DEVELOPMENT`, `QA`, `INFRASTRUCTURE`, `OTHER`.
- Transaction type: `INITIAL_ALLOCATION`, `ALLOCATION`, `ADJUSTMENT`, `INCREASE`,
  `DECREASE`, `EXPENSE`, `REFUND`, `REVERSAL`.
- Currency defaults to `INR`, with uppercase three-letter syntax validated
  by SQL. It remains a string, not a currency enum/table. Services must validate
  supported currencies. All allocation/transaction amounts use their budget's
  currency; foreign-exchange handling is not added.
- Header/allocated amounts are finite and nonnegative. Transaction amounts
  are finite and nonzero: initial funding/increase/refund must be positive,
  decrease/expense negative. Adjustment, allocation movement, and reversal
  may be either sign. Effective end cannot precede effective start.
- Department-only, employee-only, category-only (both target fields null), and
  employee-with-department-context allocations are allowed. No speculative
  uniqueness prevents multiple legitimate allocation lines of the same type.
- Optional allocation references use a same-budget composite foreign key.
  Budget-wide transactions with no allocation are supported. Every creator,
  updater, employee target, and department references the existing models.
- All new FKs use Restrict, preserving financial attribution and preventing
  cascading history loss. Project soft deletion retains budget records.
  No budget soft-delete fields or history deletion workflow is added.

### Accounting and future writer contracts

`total_budget` is the configured opening budget definition, not a cached
current balance. Future initialization must lock the budget, write exactly one
`INITIAL_ALLOCATION` matching that opening value, and activate atomically.
Do **not** add total_budget again when summing an initialized ledger: that
would double count the opening funding. Until initialization exists, treat
the ledger as uninitialized, not an authoritative zero balance.

Zero-valued draft definitions are supported, but initialization events must
be positive. Standard funded activation therefore requires a positive opening
definition. A zero-funded activation policy requires explicit future review;
it is not implemented by this foundation.

Positive movement adds funds; negative movement reduces them. For the simple
case without reversals:

- Current budget = sum of INITIAL_ALLOCATION, INCREASE, DECREASE, ADJUSTMENT.
- Available funds = current budget + signed EXPENSE and REFUND amounts.
- ALLOCATION records internal distribution changes, not new project funds;
  do not add it to the project-funding total. allocated_amount defines planned
  allocation, not consumption. Allocation-level accounting and overlapping
  department/employee plans require an explicit future service policy.

Corrections must append REVERSAL/replacement records, not overwrite ledger
history. REVERSAL needs the original event's accounting effect; sign alone
cannot distinguish reversing an expense from reversing funding. The optional
reference can carry an agreed transaction reference, but it is not a FK.
Future services must validate reversal provenance/budget and define reporting
classification before authoritative balance dashboards are introduced.

No initialization uniqueness/matching rule, append-only DB trigger, automatic
ledger writer, allocation ceiling, state machine, approval engine, payment
module, or balance/dashboard service is implemented. These contracts are
documented service requirements, not claimed database guarantees.

### Indexes and checks

Budget project uniqueness covers project lookup; status, creation time, and
creator/updater are indexed. Allocations index budget/type, department, employee,
type, creator, and creation time, with an owner/ID composite target key.
Transactions index budget/date, allocation, type, transaction date, creator,
and creation time. Leading budget prefixes cover budget-only queries.
SQL checks cover finite/nonnegative definitions, finite/nonzero signed events,
event polarity, currency syntax, and effective-date order. No new triggers or
seed records are needed.

## Payments & Payment Requests (Database Step 10)

Migration: `20261010121336_payments_payment_requests`. It adds four tables and
four enums transactionally; it does not replace earlier structures or data.
No payment, invoice, or suitable generic history model existed before this step.
Project history is project-specific, so it cannot represent these entities.

### Customer payment domain

Customer → Project → Payment Request → multiple Payments.
Payments may also be recorded directly without a formal request.
Customer payments are separate from internal project budgets: there are no
payment-to-budget foreign keys, automatic budget events, or shared balances.

| Model / table | Required fields | Nullable fields |
| --- | --- | --- |
| `PaymentRequest` / `payment_requests` | UUID id; unique paymentRequestCode (32); projectId, customerId, requestedById; amount NUMERIC(18,2); currency (3, default INR); paymentType; status (default DRAFT); requestedAt (default now); createdAt; updatedAt | description; dueDate; approvedAt/approvedById; rejectedAt/rejectedById; rejectionReason; deletedAt |
| `Payment` / `payments` | UUID id; unique paymentCode (32); projectId, customerId, recordedById; amount NUMERIC(18,2); currency (3, default INR); paymentMethod; explicit paymentDate; status (default PENDING); createdAt; updatedAt | paymentRequestId; transactionReference (255); unique receiptNumber (64); notes |
| `PaymentStatusHistory` / `payment_status_history` | UUID id; paymentId; toStatus; changedById; createdAt | fromStatus; reason |
| `PaymentRequestStatusHistory` / `payment_request_status_history` | UUID id; paymentRequestId; toStatus; changedById; createdAt | fromStatus; reason |

All timestamps are TIMESTAMPTZ(6). Prisma generates UUIDs and maintains updatedAt
on requests/payments; raw SQL writers must provide/update those values. Histories
have no updatedAt/deletedAt. A null fromStatus represents initial creation.
paymentDate is required with no default: actual receipt date must not silently
be replaced by entry creation time. requestedAt defaults to request creation.
No milestone table is needed; multiple MILESTONE requests represent staged dues.

### Enums

- `PaymentType`: ADVANCE, MILESTONE, FINAL, ADDITIONAL, AMC, RENEWAL, OTHER.
- `PaymentRequestStatus`: DRAFT, PENDING_APPROVAL, APPROVED, REJECTED, SENT,
  PARTIALLY_PAID, PAID, OVERDUE, CANCELLED.
- `PaymentMethod`: BANK_TRANSFER, UPI, CASH, CARD, CHEQUE, PAYPAL, STRIPE, OTHER.
- `PaymentStatus`: PENDING, CONFIRMED, FAILED, REVERSED, CANCELLED.

Methods classify records only; no gateway integrations are configured.

### Relationships, indexes and constraints

Requests reference Project, Customer, requester User, optional approver User,
and optional rejector User. Payments reference Project, Customer, recorder
User, and optional PaymentRequest. Each history references its parent and
changed-by User. All 13 FKs use ON DELETE RESTRICT, preserving attribution.
Codes remain globally unique even after request soft deletion. Nullable unique
receiptNumber uses PostgreSQL's ordinary unique index: multiple NULLs are
allowed, duplicate populated values are not. transactionReference is not
unique and may be reused.

Request indexes cover project/status, customer, requester/approver/rejector,
status/deletedAt, paymentType, dueDate, and createdAt. Payment indexes cover
request, project/status, customer, status, method, paymentDate, recorder, and
createdAt. Each history indexes parent/createdAt and changedById. Composite
project/status indexes cover project-only lookups without redundant indexes.

Simple SQL checks require finite positive amounts, uppercase three-letter
currency syntax, and paired approval/rejection actor-and-time fields. These
pairs do not implement an approval state machine or department restrictions.
Real currency codes and supported minor-unit precision must be validated by
future services; currencies needing more than two decimals require review.

### Calculations and future service contracts

Paid amount = SUM(amount of CONFIRMED payments linked to the request).
Remaining = requested amount minus paid; retain negative remaining as an
overpayment rather than clamping or rejecting receipt records. Multiple partial
payments and overpayments are allowed. Neither paid_amount nor remaining_amount
is stored on requests. Pending/failed/reversed/cancelled payments do not count.
Direct receipts are reported against their project/customer, not invented
request rows. Aggregate only consistent currencies; no conversion is defined.

Future services must validate request.customerId = project.customerId and,
when paymentRequestId is set, matching project/customer/currency across the
payment, request and project. Independent FKs intentionally do not enforce
these cross-entity business rules. Preserve historical ownership after receipts
exist; do not silently reassign a project's financial records to a new customer.
Code generation, Accounts authorization, retries/idempotency, duplicate external
receipt detection, status transitions, approval decisions, and overdue rules
belong to future services.

Current status updates and corresponding attributed from/to history inserts
must commit atomically. History is not auto-created by the database; future
writers must populate it and define ordering when timestamps tie.
The append-only history triggers reject UPDATE, DELETE, and TRUNCATE.

Requests follow deletedAt soft deletion. Payments have no deletedAt; preserve
them through CANCELLED/REVERSED statuses. The migration rejects physical DELETE
or TRUNCATE of **all** payments, including CONFIRMED records and records later
reversed/cancelled. This is deliberately stronger than confirmed-only retention.
Payment UPDATE remains allowed for future status/entry correction policies;
this foundation does not seal all financial fields or implement those policies.
Superuser disabling of triggers is outside ordinary application guarantees.

No receipts binary column, new file resource enum, MinIO metadata duplication,
invoice/tax/credit-note models, generic approvals, notifications, AWS services,
or financial workflow/API/UI is added. No seed data is needed.

## Common Task Engine (Database Step 11)

Migration: `20261010123004_common_task_engine`, incremental and transactional.
No common task engine previously existed. Existing project_actions remain
high-level follow-ups (payment/content/client/approval/meeting/internal actions);
tasks are executable work items. Neither replaces the other.

Project → Tasks → Workstream / Type / Assignee / Parent and Children /
Comments / Dependencies / Status History / Assignment History.

UI, UX, Development, QA, PMO and other workflows reuse this engine rather than
create separate task tables. Workstream classifies business ownership, not an
employee's current department; taskType classifies the kind of work.

### Models

| Model / table | Required fields | Nullable fields |
| --- | --- | --- |
| `Task` / `tasks` | UUID id; projectId; unique taskCode (32); title (255); taskType (GENERAL); workstream (OTHER); status (TODO); reused ProjectPriority (MEDIUM); createdById; sortOrder (0); createdAt; updatedAt | parentTaskId; description TEXT; assignedToId; startDate; dueDate; completedAt; estimatedHours/actualHours NUMERIC(10,2); deletedAt |
| `TaskDependency` / `task_dependencies` | UUID id; taskId; dependsOnTaskId; dependencyType (BLOCKS); createdAt | none |
| `TaskComment` / `task_comments` | UUID id; taskId; userId; comment TEXT; createdAt; updatedAt | none |
| `TaskStatusHistory` / `task_status_history` | UUID id; taskId; toStatus; changedById; createdAt | fromStatus; reason TEXT |
| `TaskAssignment` / `task_assignments` | UUID id; taskId; assignedToId; assignedById; assignedAt (now) | releasedAt; reason TEXT |

All timestamps are TIMESTAMPTZ(6). Prisma generates UUIDs, creation timestamps

hours are finite nonnegative Decimal summaries, not detailed time-log truth.

does not impose global sequencing; future queries need tie-breakers.

### Enums

- `TaskType`: GENERAL, DESIGN, DEVELOPMENT, TESTING, BUG_FIX, REVIEW, RESEARCH,
  DOCUMENTATION, MEETING, FOLLOW_UP, APPROVAL, DEPLOYMENT, OTHER.
- `TaskWorkstream`: PMO, BUSINESS_ANALYSIS, UI, UX, DEVELOPMENT, QA,
  PROJECT_MANAGEMENT, SALES, ACCOUNTS, HR, OTHER.
- `TaskStatus`: TODO, ASSIGNED, IN_PROGRESS, BLOCKED, IN_REVIEW, REWORK,
  COMPLETED, CANCELLED.
- `TaskDependencyType`: BLOCKS, RELATED.
- Priority reuses existing `ProjectPriority`: LOW, MEDIUM, HIGH, URGENT.
  No duplicate TaskPriority enum is introduced.

### Relationships and graph integrity

Tasks require a Project and creator User; current assignee and parent are
nullable. The self-referencing parent uses (projectId,parentTaskId) →
(projectId,id), backed by a composite unique key, so children cannot belong to
another project. A SQL check prevents direct self-parenting.

Dependencies reference two Task rows. A.taskId → B.dependsOnTaskId means A
depends on B; BLOCKS means B blocks A. RELATED is a directed stored association,
not an automatically mirrored edge. The unique
(taskId,dependsOnTaskId,dependencyType) prevents duplicates, while a check
forbids self-dependency. Different types for the same pair are permitted.
Cross-project dependencies are not prohibited by the foundation; future
authorization/policy must decide whether a particular link is appropriate.
Longer hierarchy/dependency cycles, symmetric RELATED normalization, depth,
dependency completion rules and scheduling belong to future services. There
are no recursive graph triggers or automatic status propagation.

Comments and status history reference Task and author/changer User.
Assignments reference Task, assignee User, and assigning User.
All 13 new FKs restrict deletion; no destructive parent/dependency cascades.
Parent FK updates use NO ACTION; UUID identities should remain stable.

### History and future writer contracts

Status history is append-only: UPDATE, DELETE and TRUNCATE are rejected.
Null fromStatus supports initial entries; reason is free-form, not a
department-specific enum. Current task status and its attributed history must
be written atomically by future services; no automatic history writer or
transition/state-completion-date rules are implemented.

Assignment rows preserve task, assignee, assigning actor, assignment time,
and reason. Only releasedAt on an open row may be set once, not before
assignedAt. Released rows cannot be reopened or redated, and assignment history
cannot be deleted/truncated. One SQL partial unique index permits at most one
unreleased assignment per task; any number of historical periods is supported.
It does not enforce non-overlap between arbitrary backdated closed periods.
reason describes assignment; no separate release actor/reason is added.

Future reassignment must lock the task, release the old period, insert the new
one, update tasks.assignedToId and any related status/history in one transaction.
Unassignment releases the old period and sets current assignee to NULL.
The database does not synchronize current assignee with active history:
standalone task creation/assignment is structurally valid without auto-events.
Code generation, identity/permission checks, graph validation, text validation,
status policies, date meanings and time-summary reconciliation remain services.

Tasks use deletedAt or CANCELLED rather than removing work history. Their
children/comments/dependencies/histories restrict physical deletion, and the
history guards retain attribution even after cancellation/soft deletion.
No blanket Task DELETE trigger is introduced for unused tasks without dependents.

### Indexes and deferred scope

Tasks index project/status, parent, assignee/status, creator, status/deletedAt,
priority, workstream, type, dueDate, and createdAt, plus unique code and parent
owner keys. Leading composite prefixes cover project/assignee lookup.
Dependency uniqueness covers taskId; dependsOnTaskId has a reverse index.
Comments index task/date, author, and createdAt. Status history indexes task/date,
changer, and createdAt. Assignments index task/releasedAt, assignee/assignedAt,
assigning actor, and assignedAt, plus active-period partial uniqueness.

Existing Files/ProjectResources are project-scoped. A future task-file association
can reference those files with ownership validation; no attachment join, binary
columns, second storage system, or duplicated MinIO metadata is added now.
No sprints, QA bugs, UI/UX domain tables, developer assignments, time entries,
Hubstaff integration, approvals, notifications, task-budget FKs, AWS, application
workflow, API/UI, or seed records are implemented in Step 11.
