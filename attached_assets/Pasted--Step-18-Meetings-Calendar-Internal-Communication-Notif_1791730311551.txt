# Step 18 — Meetings / Calendar / Internal Communication / Notifications

You are continuing development of the existing **InterSmart Internal ERP**.

This is **Step 18 only**.

## Objective

Implement the database layer for:

1. Internal meetings
2. Meeting participants
3. Meeting agenda/items
4. Meeting minutes
5. Meeting action items
6. Meeting status/history
7. Internal notifications
8. Notification preferences
9. Notification delivery tracking
10. Reusable reminders through the existing task/action architecture where appropriate

Do **not** implement frontend pages, APIs, controllers, services, WebSocket handlers, email workers, cron jobs, or notification automation in this step.

# 2. MEETINGS

Create:

## `meetings`

Fields:

- `id` UUID PK
- `meeting_code` UNIQUE
- `title`
- `description` nullable
- `meeting_type`
- `status`
- `organizer_id` FK → users
- `project_id` nullable FK → projects
- `customer_id` nullable FK → customers
- `start_at`
- `end_at`
- `location` nullable
- `meeting_url` nullable
- `agenda` nullable
- `minutes` nullable
- `created_at`
- `updated_at`
- `cancelled_at` nullable
- `cancelled_by_id` nullable → users
- `cancellation_reason` nullable

Meeting types:

```text
INTERNAL
CUSTOMER
PROJECT
TEAM
MANAGEMENT
HR
INTERVIEW
REVIEW
OTHER
```

Meeting statuses:

```text
SCHEDULED
IN_PROGRESS
COMPLETED
CANCELLED
NO_SHOW
```

Use `DateTime` for `start_at` and `end_at`.

Do not store duration separately.

Duration should be calculated from:

```text
end_at - start_at
```

# 6. MEETING MINUTES

Although the meeting model contains a general `minutes` field, structured minutes are required for important meetings.

Create:

## `meeting_minutes`

Fields:

- `id` UUID PK
- `meeting_id` UNIQUE FK
- `summary`
- `decisions` nullable
- `created_by_id` FK → users
- `approved_by_id` nullable FK → users
- `approved_at` nullable
- `created_at`
- `updated_at`

Do not create multiple minute records for the same meeting unless the existing architecture explicitly requires versioning.

The simple model should be:

```text
Meeting
  └── one Meeting Minutes
```

# 7. MEETING ACTION ITEMS

Reuse the existing common task engine wherever the action represents executable work.

Do NOT create:

```text
meeting_tasks
meeting_action_tasks
```

Instead, use:

```text
tasks.task_type = MEETING
```

and:

```text
tasks.workstream
```

based on the responsible department/workstream.

If the existing task architecture supports a generic reference/link pattern, use it.

If not, create:

## `meeting_task_links`

Fields:

- `id`
- `meeting_id`
- `task_id`
- `created_at`

Constraints:

- Unique `meeting_id + task_id`

This allows a meeting to produce multiple executable tasks.

Do not duplicate:

- task assignment
- task status
- task comments
- task history

Use the existing task engine.

# 13. NOTIFICATION READ STATE

The notification itself should represent a notification for one user.

Do not create a separate `notification_recipients` table unless the existing design specifically requires one notification to be independently addressed to many users.

For now:

```text
notification
    ↓
one recipient
```

If the same event needs to notify 10 employees, create 10 notification records.

This keeps read/unread state simple.

# 16. REMINDERS

Do not create a separate reminder engine.

For meeting reminders, future application logic can generate notifications based on:

```text

```

For task reminders:

```text

```

For project actions:

```text
project_actions.due_date
```

Do not store duplicated reminder timestamps unless there is a clear business requirement.

# 22. SECURITY

Notifications may expose business-sensitive information.

Application-level authorization must later ensure that a user only receives notifications they are permitted to see.

Do not rely on:

```text
entity_type
entity_id
```

as an authorization mechanism.

Those fields are references only.

The backend must validate access to the referenced entity before creating or returning sensitive notifications.
