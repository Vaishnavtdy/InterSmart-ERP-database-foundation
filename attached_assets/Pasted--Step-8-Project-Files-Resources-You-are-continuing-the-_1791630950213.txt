### Important storage architecture

Actual file binaries will eventually be stored in:

> **MinIO**

PostgreSQL must store **only file metadata and business relationships**.

Do NOT store binary file contents, base64 data, blobs, or large file data inside PostgreSQL.

Do NOT introduce AWS S3 or any AWS SDK.

The storage abstraction should remain compatible with self-hosted MinIO.

# 3. Create the `files` model

Create a `files` table/model representing the physical stored file.

Recommended fields:

```text
id
project_id
uploaded_by_id
file_name
original_name
storage_key
bucket
mime_type
size_bytes
checksum
version
is_current
created_at
updated_at
deleted_at
```

### Field requirements

#### `id`

- UUID
- Primary key

#### `project_id`

- Foreign key to `projects`
- A project file normally belongs to a project
- Follow the existing relation conventions

If the existing architecture strongly benefits from allowing non-project files, document that decision before making the field nullable. Do not introduce unnecessary global file management.

#### `uploaded_by_id`

- Foreign key to `users`
- Required
- Represents the employee who uploaded the file

#### `file_name`

The internal/safe filename used by the storage layer.

#### `original_name`

The original filename uploaded by the employee.

Example:

```text
Company_Profile.pdf
```

#### `storage_key`

The MinIO object key.

Example:

```text
projects/{project-id}/brand-book/{uuid}-Company_Profile.pdf
```

This must be unique.

#### `bucket`

The MinIO bucket containing the object.

Example:

```text
company-files
```

Do not hard-code this value into the schema as an enum because the storage configuration may change.

#### `mime_type`

Example:

```text
application/pdf
image/png
image/jpeg
application/vnd.openxmlformats-officedocument.wordprocessingml.document
```

#### `size_bytes`

Use an appropriate integer type capable of storing large file sizes.

Do not use floating point.

#### `checksum`

Store the checksum/hash of the stored file when available.

Use a string field.

This can later be used for:

- duplicate detection
- integrity verification
- upload validation

#### `version`

Integer version number.

Example:

```text
1
2
3
```

#### `is_current`

Boolean indicating whether this is the current version.

Historical files must not be physically overwritten when versioning is used.

#### `deleted_at`

Nullable soft-delete timestamp, following the existing project/database conventions.

# 6. Why separate `files` and `project_resources`

Keep the responsibilities separate.

### `files`

Represents:

> Where and how the physical file is stored.

Example:

```text
storage_key
bucket
mime_type
size_bytes
checksum
```

### `project_resources`

Represents:

> What the file means to the project.

Example:

```text
resource_type = BRAND_BOOK
title = "Client Brand Guidelines"
```

This separation will allow us later to support:

- multiple business references to files
- version history
- controlled access
- MinIO storage
- resource categorization
- future file approval workflows
- project-specific resource views

Do not duplicate MinIO metadata unnecessarily in `project_resources`.

---

# 7. File versioning

Design the models so that a new version does not overwrite the previous physical file.

Example:

```text
Brand Book v1
Brand Book v2
Brand Book v3
```

All historical versions should remain represented in the database.

The current version should be identifiable using:

```text
is_current = true
```

Older versions:

```text
is_current = false
```

Do not physically delete old versions as part of this step.

If enforcing "only one current version" requires a PostgreSQL partial unique index that Prisma cannot cleanly represent using the project's current Prisma version/configuration, do not introduce a fragile workaround.

Instead:

- maintain the application-level rule
- add the normal indexes/constraints that Prisma supports
- document the limitation and future enforcement option

---

# 8. MinIO storage key convention

Document a standard storage-key structure.

Recommended pattern:

```text
projects/{project-id}/{resource-type}/{uuid}-{safe-filename}
```

Example:

```text
projects/8f1.../BRAND_BOOK/4a2...-brand-guidelines.pdf
```

The database should store the complete `storage_key`.

Do not depend on the original filename being unique.

Do not allow user-provided filenames to become unrestricted storage paths.

The future upload service will sanitize filenames and generate the unique object key.

---

# 9. Security considerations

The database design must support secure file access.

Do NOT design files as publicly accessible URLs.

Do NOT store permanent public URLs as the source of truth.

Future application flow should be:

```text
Employee
   ↓
Next.js
   ↓
NestJS authorization
   ↓
Check project/resource permissions
   ↓
Generate controlled MinIO access
   ↓
Employee accesses file
```

The database should therefore store:

```text
bucket
storage_key
```

rather than relying on a public URL.
