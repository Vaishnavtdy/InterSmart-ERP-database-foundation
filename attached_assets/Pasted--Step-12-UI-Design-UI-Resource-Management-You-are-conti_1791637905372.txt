# 3. Important architecture rule

Do NOT create a separate task system.

The existing common task engine from Step 11 must be reused.

Conceptually:

```text id="q8f4m2"
Project
   │
   ├── UI Specification
   │
   ├── UI Pages
   │
   ├── UI Sections
   │
   └── Common Tasks
          ↓
       UI workstream
```

UI-specific metadata belongs in UI tables.

Actual executable work belongs in the common `tasks` table.

This represents the UI design definition for the project.

It should contain information such as:

- UI title
- design description
- UI requirements
- design status

# 13. Page URL

`url` should be nullable.

Some UI pages may not have a finalized URL during design.

Do not make it unique globally.

Two projects can have:

```text id="b7k2m9"
/about
```

without conflict.

If uniqueness is required, it should be scoped to the project.

# 21. Link tasks to UI pages

The common `tasks` table needs to know which UI entity the task relates to.

Do not add fields like:

```text id="m5q8x2"
ui_page_id
ui_section_id
```

to `tasks` if this would make the common task engine tightly coupled to UI.

Instead, create a domain relationship model:

```text id="r8v3p6"
ui_task_links
```

Recommended:

```text id="n4m7x2"
id
task_id
ui_page_id
ui_section_id
created_at
```

Rules:

- `task_id` required
- `ui_page_id` required
- `ui_section_id` nullable

This allows:

```text id="y5q2n8"
Task → Page
```

or:

```text id="w3m7p4"
Task → Page → Section
```

without polluting the generic task model.

# 25. Completion percentage



# 26. Daily status uniqueness

A project UI should normally have at most one daily status for a date.

Use:

```text id="m5q8v3"
project_ui_id + status_date
```

as a unique constraint.

This prevents duplicate daily status entries for the same UI specification/date.

# 32. UI progress

Do NOT add:

```text id="m9q2x7"

```

to `projects`.

- UI page statuses
- UI tasks
- daily status
- approved/reviewed work

---

# 33. UI history

Do not create separate history tables for every UI entity unless required.

At minimum:

- UI daily status provides reporting history.
- Common tasks provide task status history.
- Existing project status history covers project-level state.

If later audit requirements need page/section status history, it can be added deliberately.

Do not over-engineer this step.

---

# 35. UI scope relationship

UI pages should be consistent with:

```text id="w4n8q2"

```

but do not create a direct mandatory foreign key unless the existing business process requires it.

Reason:

A scope item such as:

```text id="j3p7v9"

```

may not map one-to-one to a page.

The relationship can be handled at the application/domain level later.

# 38. Important constraints

At minimum:

```text id="n3v7q2"
project_ui.project_id + version_number
```

should be unique.

For daily status:

```text id="x8m4p6"
project_ui_id + status_date
```

should be unique.

For UI task links, prevent accidental duplicate links where appropriate.

For example:

```text id="r5q9m3"
task_id + ui_page_id + ui_section_id
```

If nullable uniqueness is problematic in PostgreSQL/Prisma, implement a sensible application-level duplicate check and document it.
