# 2. Important domain separation

There are two different financial concepts in this ERP.

## Internal project budget

Already implemented in Step 9:

```text
Project
   ↓
Project Budget
   ↓
Budget Allocations
   ↓
Budget Transactions
```

This represents internal project execution budget.

## Customer payments

This step represents:

```text
Customer
   ↓
Project
   ↓
Payment Request
   ↓
Customer Payment
```

This represents money that the customer is expected to pay or has paid.

These two domains MUST remain separate.

Do not connect customer payments directly to `budget_transactions`.

# 6. Project relationship

Every payment request should normally belong to a project.

```text id="bjxw2n"
payment_requests.project_id
    → projects.id
```

This allows the ERP to answer:

- How much has this project requested?
- How much has the customer paid?
- Which project has pending payment?
- Which project requires payment follow-up?

---

# 7. Customer relationship

Also connect payment requests to the customer.

```text id="08f4bw"
payment_requests.customer_id
    → customers.id
```

Although the project already points to a customer, explicitly storing the customer on the payment request provides:

- historical consistency
- simpler queries
- easier reporting

However, document that application logic must ensure:

```text id="n89w3y"
payment_requests.customer_id
=
projects.customer_id
```

for project-based payment requests.

Do not use a database trigger unless the existing architecture requires one.

# 16. Payment request relationship

A payment should normally be associated with a payment request:

```text id="12u3yx"
payments.payment_request_id
    → payment_requests.id
```

However, make this relationship nullable.

Reason:

Sometimes Accounts may record a payment directly when there was no formal payment request.

Example:

```text id="qv3j7h"
Customer transferred money directly.
Accounts records payment manually.
```

Therefore:

```text id="r8t5pl"
payment_request_id = nullable
```

---

# 26. Payment allocation / partial payments

A payment request may be paid in multiple transactions.

Example:

```text id="m4d7v0"
Payment Request:
₹100,000

Payment 1:
₹40,000

Payment 2:
₹30,000

Payment 3:
₹30,000
```

The schema must therefore support:

```text id="q1e4cv"
payment_request
    ↓
multiple payments
```

Do NOT put:

```text id="x6c8yz"
paid_amount
remaining_amount
```

as source-of-truth fields on `payment_requests`.

These should be calculated from confirmed payments.

---

# 27. Payment calculations

Eventually:

```text id="8a3p7w"
Requested Amount
=
payment_request.amount
```

and:

```text id="6f4c1n"
Paid Amount
=
SUM(confirmed payments associated with the request)
```

and:

```text id="p3q7k1"
Remaining Amount
=
Requested Amount - Paid Amount
```

These are calculated values.

Do not store them as duplicated source-of-truth columns.

---

# 28. Overpayment

The system must not silently lose overpayments.

Example:

```text id="0g9b8v"
Requested = ₹100,000
Paid = ₹110,000
```

The database should allow the payment record to exist.

Do not add complicated automatic accounting logic in this migration.

The application/reporting layer can later identify:

```text id="8m4q5k"
overpayment = ₹10,000
```

and handle it according to company policy.

---

# 29. Payment receipts/files

Do not create a dedicated binary receipt column.

Payment receipts may eventually use the existing Step 8 file system:

```text id="v3h7cx"

project_resources
```

However, do not force a payment-specific resource type into Step 8 unless genuinely needed.

If receipt attachments are required later, they can be associated through a clean file/reference model.

Do not duplicate MinIO metadata inside `payments`.

# 30. Customer payment vs project budget

This distinction is critical.

Example:

```text id="1h7w9m"
Customer pays:
₹500,000
```

This does NOT automatically mean:

```text id="l2r5qp"
Project budget = ₹500,000
```

They are independent financial concepts.

Customer payment:

```text id="x4g7v2"
Money received from customer
```

Project budget:

```text id="e7k2z8"
Internal project execution budget
```

Do not create automatic foreign-key or transaction relationships between them.

# 33. Soft deletion

Follow the existing project's soft-delete convention.

If existing business entities use:

```text id="r7y2pz"
deleted_at
```

then `payment_requests` should follow the same convention.

Do not casually soft-delete financial transaction records if doing so would destroy financial history.

For actual `payments`, prefer preserving the record and using:

```text id="d3v8j1"
CANCELLED
REVERSED
```

where appropriate.

Do not physically delete confirmed financial records.

Document this decision.
