# Step 17 — HR / Leave / Performance / Complaints / Appreciation

You are continuing development of the existing **InterSmart Internal ERP**.

This is **Step 17 only**.

## Objective

Implement the HR management database layer for:

1. Leave management
2. Leave balances
3. Leave requests and approvals
4. Performance management
5. Performance goals
6. Employee feedback
7. HR complaints
8. Complaint status/history

- `name`

- SICK
- ANNUAL
- EMERGENCY
- MATERNITY
- PATERNITY

Do not hard-code these values as database rows unless seed data already exists in the project.

---

# 3. LEAVE BALANCES

Create:

## `leave_balances`

Fields:

- `id` UUID PK
- `user_id` FK → users
- `leave_type_id` FK → leave_types
- `year`
- `allocated_days` Decimal
- `used_days` Decimal
- `pending_days` Decimal
- `adjusted_days` Decimal
- `created_at`
- `updated_at`

Constraints:

- Unique: `user_id + leave_type_id + year`

Important:

Do not store `remaining_days` as a source-of-truth field.

Remaining leave should be calculated as:

```text
allocated_days
+ adjusted_days
- used_days
- pending_days
```

# 18. SECURITY / PRIVACY

HR information is more sensitive than normal project data.

Design the schema so that later application-level authorization can enforce:

- Employees can view their own leave information.
- Employees can create their own leave requests.
- Authorized managers/HR can approve leave.
- Employees can access their own performance review information according to workflow.
- HR can manage performance records.
- Complaint records are restricted to authorized HR/management users.
- Confidential complaints must have additional authorization checks.
- Employee appreciation visibility must be respected.

Do not implement authorization logic in this migration.

Only prepare the database correctly.

---

# 19. AUDITABILITY

Use status-history tables for:

- Leave requests
- HR complaints

Performance and appreciation records should retain timestamps and responsible users.

Do not physically delete finalized financial or HR history.

Where appropriate, use:

```text
deleted_at
```

for soft deletion rather than hard deletion.
