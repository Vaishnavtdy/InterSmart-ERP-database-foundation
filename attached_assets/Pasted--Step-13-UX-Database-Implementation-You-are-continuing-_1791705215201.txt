# Step 13 — UX Database Implementation

You are continuing the incremental database implementation for the InterSmart internal ERP.

## Current architecture

The application is for **one organization: InterSmart**.

Important architecture rules:

- Do NOT create an `organizations` table.
- Do NOT add `organization_id` or `tenant_id`.
- `users` are internal InterSmart employees.
- `customers` are external clients and do not authenticate.
- Use PostgreSQL + Prisma.
- Use UUID primary keys.
- Use `DateTime` / PostgreSQL `timestamptz` for timestamps.
- Use `Decimal` / PostgreSQL numeric types for monetary values.
- Existing project, team, task, file, budget, payment, UI, and other models must be reused.
- Do NOT create AWS-specific infrastructure.
- Do NOT reset the database.
- Do NOT delete or rewrite existing migrations.
- Create a new Prisma migration for this step only.

The following database modules already exist:

1. Users / Departments / Employee Profiles
2. Roles / Permissions

# 1. Create `project_ux`

Create a `project_ux` model representing a UX version/workstream for a project.

Suggested fields:

```text
id
project_id
version_number
title
description
status
research_summary
user_personas
user_journey_summary
created_by_id
approved_by_id
approved_at
created_at
updated_at
```

Relationships:

```text
project -> Project
created_by -> User
approved_by -> User
screens
flows
ux_task_links
daily_statuses
design_links
```

### Rules

- `project_id` must reference `projects`.
- `version_number` must be unique per project.
- Add a composite unique constraint:

```text
(project_id, version_number)
```

- `approved_by_id` is nullable.
- `approved_at` is nullable.
- `description`, `research_summary`, `user_personas`, and `user_journey_summary` may be nullable.

Do not store calculated progress on `project_ux`.


# 6. Connect UX work to the common task engine

Create:

```text

```

Fields:

```text

project_ux_id

```

Rules:

- `task_id` references existing `tasks`.
- `project_ux_id` references `project_ux`.
- `ux_screen_id` is nullable.
- `ux_flow_id` is nullable.
- At least one UX context should normally be provided, but do not implement complicated database-level CHECK constraints unless the existing project architecture already uses them.
- Add appropriate indexes.

This allows:

```text

```

The task itself remains generic.

For UX tasks:


If `RESEARCH` does not currently exist in the existing `TaskType`, inspect the existing enum and extend it only if necessary.

# 14. Referential integrity

Follow the existing Prisma relationship conventions.

Expected behavior:

- A project cannot be deleted while referenced by UX records unless the existing architecture uses soft deletion/cascade.
- A UX version should not silently disappear when a user is deleted.
- `created_by_id` should preserve historical ownership.
- `approved_by_id` should be nullable.
- UX screens should belong to a UX version.
- UX flows should belong to a UX version.
- Flow steps should belong to a flow.
- UX task links should reference existing tasks.

Use the same `onDelete` conventions already established in the schema.

Do not introduce a completely different relationship strategy.
