# Step 21 — Master Data / ERP Configuration / Business Rules

You are continuing development of the existing **InterSmart Internal ERP**.

This is **Step 21 only**.

## Objective

Implement a controlled configuration and master-data layer for business values that need to be managed by authorized administrators.

The goal is to avoid hard-coding every business classification while keeping the core ERP schema strongly typed and relational.

This step should cover:

1. Business master data
2. Configurable project categories
3. Configurable task/workstream metadata where appropriate
4. Customer/lead source configuration
5. Payment configuration
6. Leave configuration support
7. System business settings
8. Number/code configuration
9. Controlled feature flags
10. Configuration auditability

Do NOT implement frontend configuration screens, APIs, controllers, services, or admin UI in this step.

---

# 1. IMPORTANT ARCHITECTURE RULE

Before making any change:

- Inspect the complete Prisma schema.
- Reuse existing master tables.
- Do not create duplicate category tables.
- Do not replace existing enums unnecessarily.
- Do not convert every enum into a database table.
- Do not create an unrestricted key/value configuration system.
- Do not create `organization_id`.
- Do not introduce AWS.
- Do not create a second authorization system.
- Do not create another audit system.

The goal is **controlled configurability**, not a generic CMS.

# 12. SEQUENCE SAFETY

The future application service must generate codes atomically.

The database design must prevent two simultaneous requests from generating the same number.

Do not implement the sequence service in this step.

Do not use:

```text
SELECT current_value
UPDATE current_value
```

without transaction/locking in the future implementation.

The sequence row should be updated atomically.

---

# 13. SYSTEM BUSINESS SETTINGS

Do NOT create a completely generic key/value settings table.

Instead create a controlled model:

## `system_settings`

Fields:

- `id`
- `key` UNIQUE
- `value`
- `value_type`
- `description` nullable
- `is_sensitive`
- `is_editable`
- `updated_by_id` FK → users
- `created_at`
- `updated_at`

Allowed `value_type`:

```text
STRING
INTEGER
DECIMAL
BOOLEAN
DATE
JSON
```

Important:

This table is for **non-secret business configuration only**.

Examples:

```text
default_project_currency
default_task_due_days
default_notification_expiry_days
company_timezone
default_leave_year_start
```

Do NOT store:

```text
SMTP password
MinIO secret
database password
JWT secret
API keys
private keys
AWS credentials
```

Secrets belong in environment/secret-management infrastructure.

---

# 14. SENSITIVE SETTING RULE

Although `is_sensitive` may identify settings that need restricted access, do NOT use this table as a secret store.

A future application layer can use:

```text
is_sensitive = true
```

to restrict visibility for non-sensitive business configuration.

But credentials must still remain outside PostgreSQL.

# 16. FEATURE FLAG VS PERMISSION

Do not confuse:

```text
feature flag
```

with:

```text
permission
```

Feature flag:

> Is this product capability enabled?

Permission:

> Is this user allowed to use it?

Continue using:

```text
roles
permissions
user_roles
role_permissions
```

for authorization.

# 23. NO GENERIC CONFIGURATION JSON

Do not create something like:

```text

key
value_json
```

for everything.

Configuration that has relationships or business meaning should be modeled relationally.

JSON is appropriate only when the value is genuinely configuration metadata.

# 24. MIGRATION STRATEGY

Before changing an existing field:

1. Inspect how it is currently used.
2. Determine whether data already exists.
3. Do not destroy existing values.
4. Create the new master records.
5. Migrate existing values safely.
6. Add the foreign key.
7. Remove the old field only when safe.

If there is no existing data, prefer the cleanest final schema.

Do not use destructive migration shortcuts.
