# Step 19 — Dashboard / Reporting / KPI Data Layer

You are continuing development of the existing **InterSmart Internal ERP**.

This is **Step 19 only**.

## Objective

Prepare the database architecture required for:

1. Management dashboard
2. Sales dashboard
3. Accounts dashboard
4. PMO dashboard
5. Project Coordinator dashboard
6. UI dashboard
7. UX dashboard
8. Development dashboard
9. QA dashboard
10. HR dashboard
11. Employee/team performance reporting
12. Project KPI reporting
13. Financial KPI reporting
14. Operational reporting
15. Saved report configurations

The most important rule for this step:

> **Do not store dashboard numbers as source-of-truth data.**

Dashboards must calculate their values from the existing transactional tables.

Do not build frontend dashboards in this step.

Do not build APIs/controllers/services in this step.

---

# 1. ARCHITECTURE RULE

Before changing anything:

- Inspect the complete Prisma schema.
- Understand all existing relationships.
- Reuse existing transactional tables.
- Do not duplicate business data.
- Do not add calculated fields to `projects`, `users`, `tasks`, payments, budgets, etc.
- Do not create a separate reporting database.
- Do not introduce a data warehouse.
- Do not introduce AWS.
- Do not create materialized dashboard tables unless there is a demonstrated performance requirement.
- Do not create separate dashboard tables for each department.

The ERP database remains the primary source of truth.

# 4. REPORT CONFIGURATIONS

Create:

## `report_configurations`

Fields:

- `id` UUID PK
- `report_id` FK
- `configuration`
- `version`
- `created_by_id` FK → users
- `created_at`
- `updated_at`

`configuration` may use JSON/JSONB because this is configuration metadata rather than transactional business data.

Examples of configuration:

```text id="3gg0qa"

grouping

```

Do not put actual report results in this JSON.

Do not use JSONB for transactional data.


# 11. KPI TARGETS

Create:

## `kpi_targets`

Fields:

- `id` UUID PK
- `kpi_definition_id` FK
- `target_value` Decimal
- `effective_from`
- `effective_until` nullable
- `created_by_id` FK → users
- `created_at`
- `updated_at`

This allows:

```text id="c2qj34"

2027 target
quarterly target
department target
```

without changing the KPI definition.

Do not store current actual KPI values.

# 19. PERFORMANCE CONSIDERATIONS

The first implementation should use PostgreSQL queries against normalized tables.

Do not prematurely introduce:

- materialized views
- Elasticsearch
- ClickHouse
- data warehouse
- Redis dashboard cache
- separate analytics database

If performance becomes an actual problem later, optimize the specific queries.

Possible future optimizations:

```text id="7xqk4q"
indexes
materialized views
cached metrics
precomputed aggregates
reporting database
```

These are future concerns.

Reuse:


```text id="7f4x8c"

```

Do not automatically grant these permissions to every role.

For example:

- Employee → own permitted dashboard
- Team lead → team-related dashboard
- PMO → project/operations dashboard

- HR → HR dashboard
- Management → global dashboard

Do not hard-code these rules inside the database.
