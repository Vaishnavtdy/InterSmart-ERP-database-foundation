# Step 14 — Development Database Implementation

You are continuing the incremental database implementation for the InterSmart internal ERP.

## Current architecture

The application is for **one organization: InterSmart**.

Important architecture rules:

- Do NOT create an `organizations` table.
- Do NOT add `organization_id` or `tenant_id`.
- `users` are internal InterSmart employees.
- `customers` are external clients and do not authenticate.
- PostgreSQL + Prisma.
- UUID primary keys.
- PostgreSQL `timestamptz` through Prisma `DateTime`.
- `Decimal` for monetary values.
- Existing projects, tasks, teams, files, budgets, payments, UI, and UX models must be reused.
- No AWS services.
- Do NOT reset the database.
- Do NOT delete or rewrite old migrations.
- Create a new migration only for this step.

# 15. Development sprint rules

Sprints must support:

```text
PLANNED
ACTIVE
COMPLETED
CANCELLED
```

A typical lifecycle:

```text
PLANNED
   ↓
ACTIVE
   ↓
COMPLETED
```

Alternative:

```text
PLANNED
   ↓
CANCELLED
```

Tasks can be:

- created before a sprint
- assigned to a sprint later
- moved between sprints if business rules permit
- completed independently of sprint completion

Do not enforce complex sprint/task business rules at database level unless the existing architecture already does so.
