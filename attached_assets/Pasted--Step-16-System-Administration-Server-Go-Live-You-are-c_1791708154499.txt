# Step 16 — System Administration / Server / Go-Live

You are continuing the incremental database implementation for the InterSmart internal ERP.

## Current architecture

The application is for **one organization: InterSmart**.

Important architecture rules:

- Do NOT create an `organizations` table.
- Do NOT add `organization_id` or `tenant_id`.
- `users` are internal InterSmart employees.
- `customers` are external clients and do not authenticate.
- PostgreSQL + Prisma.
- UUID primary keys.
- PostgreSQL `timestamptz` through Prisma `DateTime`.
- `Decimal` for monetary values.
- No AWS services.
- Infrastructure may use self-hosted servers, VPS, Docker, Nginx, MinIO, PostgreSQL, Redis, etc.
- Do NOT store passwords, API keys, SSH private keys, tokens, or other secrets in PostgreSQL.
- Existing Project, Task, Sprint, Development, QA, File, Team, and Deployment models must be reused.
- Do NOT reset the database.
- Do NOT delete or rewrite previous migrations.
- Create a new migration only for this step.

# CRITICAL SECURITY RULE

The ERP must NEVER store:

- SSH private keys
- SSH passwords
- server passwords
- database passwords
- API keys
- access tokens
- cloud secrets
- SMTP passwords
- MinIO secret keys
- Git credentials
- TLS private keys

Do not add generic fields such as:

```text id="0v1x5r"
password
secret
private_key
api_key
access_token
credential
```

to infrastructure models.

If credentials need to be referenced, store only:

```text id="n9m7w2"
credential_reference
```

or:

```text id="4f2j8c"
credential_name
```

meaning a reference to an external secure secret manager/password manager.

The actual secret must remain outside PostgreSQL.
