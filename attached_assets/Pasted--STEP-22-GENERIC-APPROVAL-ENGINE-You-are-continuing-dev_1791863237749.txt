# Objective

Create a **generic approval engine** that can be reused by different ERP modules.

The approval engine must support use cases such as:

- Payment request approval
- Out-of-scope approval
- Budget increase approval
- Development correction approval
- Sprint approval
- Meeting approval
- Other future business approvals

The approval engine must track the approval workflow without replacing the business status/history of the originating module.

# 2. Create `approval_requests`

Create:

```text
approval_requests
```

Fields:

```text
id UUID PK

request_code String UNIQUE

request_type String

entity_type String
entity_id UUID

requested_by_id UUID FK -> users.id

status ApprovalRequestStatus

priority ApprovalPriority

reason String nullable

due_at DateTime nullable

current_step_order Integer nullable

completed_at DateTime nullable
cancelled_at DateTime nullable

created_at DateTime
updated_at DateTime
```

### Purpose

This represents one approval workflow attached to a business entity.

Examples:

```text
request_type = PAYMENT_REQUEST
entity_type = PAYMENT_REQUEST
entity_id = paymentRequestId
```

or:

```text
request_type = OUT_OF_SCOPE
entity_type = PROJECT
entity_id = projectId
```

`entity_type + entity_id` is a generic reference and is NOT a database foreign key.

Authorization must never depend only on `entity_type/entity_id`.

# 6. Approver Type

```text
ApprovalApproverType
```

Values:

```text
USER
ROLE
DEPARTMENT

```

Rules:

### USER

Specific employee must approve.

Use:

```text
approver_user_id
```

### ROLE

Any authorized user with the specified role may approve.

Use:

```text
approver_role_id
```

### DEPARTMENT

Approval is assigned to an appropriate employee within a department.

Use:

```text
approver_department_id
```

### MANAGER

The responsible manager is resolved by application logic.

Do NOT create a separate manager table.

# 12. Approval Workflow Rules

The database should support this workflow:

```text
DRAFT
   ↓
PENDING
   ↓
Step 1
   ↓
Step 2
   ↓
Step N
   ↓
APPROVED
```

Possible outcomes:

```text
PENDING → REJECTED
PENDING → RETURNED
PENDING → CANCELLED
PENDING → EXPIRED
```

A returned request may later be resubmitted by application logic.

Do not implement workflow logic inside database triggers.

---

# 13. Sequential Approval

The schema must support sequential approvals.

Example:

```text
Step 1 → PMO
Step 2 → Accounts
Step 3 → Management
```

Only the currently active step should normally be actionable.

Use:

```text
step_order
current_step_order
```

to support this.

Do not create separate approval tables for PMO, Accounts, Sales, Development, etc.

---

# 14. Parallel Approval Support

The schema should also allow multiple approvers at the same `step_order`.

Example:

```text
Step 1:
    User A
    User B

Step 2:
    Accounts
```

Do not introduce a complicated workflow graph or BPMN engine.

The application layer will determine whether all or any approvers are required.

# 19. Domain Module Rules

IMPORTANT:

The approval engine does NOT replace domain-specific workflow tables.

For example:

Payment:

```text
payment_request
payment_request_history
approval_request
approval_steps
approval_history
```

Project out-of-scope:

```text
project scope data
domain history
approval_request
approval_steps
approval_history
```

The approval engine tracks:

> "Was this request approved?"

The domain module tracks:

> "What happened to the actual business entity?"

Do not merge these responsibilities.
