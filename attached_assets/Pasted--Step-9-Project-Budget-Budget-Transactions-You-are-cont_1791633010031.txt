# 3. Important architecture rule

Do NOT put budget fields directly into the `projects` table.

Do NOT add fields such as:

```text
budget
used_budget
remaining_budget
budget_status
```

to `projects`.

Budget is a separate financial domain.

The relationship should be:

```text
Project
   │
   └── Project Budget
          │
          ├── Budget Allocations
          │
          └── Budget Transactions
```

This allows budget history and multiple adjustments without corrupting the project record.

## Field requirements

### `id`

- UUID
- Primary key

### `project_id`

- Foreign key to `projects`
- Required

A project should have a clear budget record.

Use a unique constraint if the business model supports only one active/current budget definition per project.

If historical budget versions are required by the existing architecture, document the approach rather than creating duplicate active budgets.

### `total_budget`

Use:

```text
Decimal / PostgreSQL NUMERIC
```

Never use floating-point types for money.

### `currency`

String field.

For example:

```text
INR
```

Do not unnecessarily create a currency table at this stage.

The system can later support additional currencies if required.

### `status`

Create a budget status enum.

Recommended values:

```text
DRAFT
ACTIVE
ON_HOLD
CLOSED
CANCELLED
```

### `effective_from`

Date/time when the budget becomes applicable.

### `effective_until`

Nullable date/time.

### `notes`

Optional explanation or financial notes.

### `created_by_id`

Foreign key to `users`.

### `updated_by_id`

Nullable foreign key to `users`.

### timestamps

Use the project's existing:

```text
created_at
updated_at
```

conventions.

# 6. Allocation design

An allocation may belong to:

- a department
- an individual employee
- a functional category

Do not force every allocation to require a user.

Examples:

### Department allocation

```text
Development → ₹100,000
```

### Employee allocation

```text
Developer A → ₹40,000
```

### Functional allocation

```text
QA → ₹25,000
```

Therefore:

```text
department_id = nullable
user_id = nullable
allocation_type = required
```

Do not allow both `department_id` and `user_id` to become mandatory.

# 10. Transaction types

```text
INITIAL_ALLOCATION
ALLOCATION
ADJUSTMENT

DECREASE
EXPENSE
REFUND

```

These represent financial changes.

Do not create separate columns such as:

```text
increase_amount

```

The transaction model should remain normalized.

---

# 11. Positive/negative amount convention

Choose one consistent convention and document it.

Recommended:

```text
amount > 0
```

means a positive budget movement.

```text
amount < 0
```

means a reduction.

Examples:

### Budget increase

```text
+50,000
```

### Budget reduction

```text
-10,000
```

### Expense

```text
-5,000
```

### Refund

```text
+2,000
```

Do not store both positive and negative values for the same financial event in separate fields.

---

# 12. Important accounting principle

Do not store calculated values such as:

```text
used_budget
remaining_budget
available_budget
```

as source-of-truth columns.

These values should eventually be calculated from transactions.

Conceptually:

```text
Current Budget
=
Initial Budget
+
Budget Increases
-
Budget Decreases
+
Adjustments
```

and:

```text
Available Budget
=
Current Budget
-
Expenses
```

The exact calculation can be implemented later in services/reporting.

For this database step, preserve the underlying transactions.

---

# 13. Transaction reference

`reference` should be optional.

It may later contain:

```text
payment request ID
expense reference
approval ID
invoice reference
manual adjustment reference
```

Do not create foreign keys to future tables that do not exist yet.

Do not use a polymorphic foreign-key implementation at this stage.

Simply store a reference string if needed.

Document that future domain tables may introduce stronger relationships.

---

# 14. Allocation relationship

`allocation_id` should be nullable.

Why?

Some transactions may apply to the overall project budget rather than a specific allocation.

Examples:

```text
Project-wide budget increase
Project-wide adjustment
Project-wide refund
```

Therefore:

```text
budget_transactions.allocation_id
```

should be nullable.

# 18. Example data model

The resulting structure should conceptually look like:

```text
PROJECT
   │
   └── PROJECT_BUDGET
          │
          ├── BUDGET_ALLOCATION
          │      ├── Department
          │      └── User
          │
          └── BUDGET_TRANSACTION
                 └── optional Allocation
```

Example:

```text
Project: ABC Website

Budget:
₹500,000

Allocations:

UI:
₹80,000

UX:
₹60,000

Development:
₹250,000

QA:
₹70,000

PM:
₹40,000
```

Transactions might then be:

```text
INITIAL_ALLOCATION +500,000

EXPENSE -20,000
EXPENSE -15,000

INCREASE +50,000

EXPENSE -30,000
```

The application can later calculate the current financial state from these records.
